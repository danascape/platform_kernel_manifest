The two versions give byte-identical results. 0.73.2 does not fix it.

The libclang pairing was verified rather than assumed, which is the one
way this test could have produced a clean-looking lie:

  $ LIBCLANG_PATH=<empty dir> bindgen x.h
  thread 'main' panicked: Unable to find libclang: "couldn't find any
  valid shared libraries matching: ['libclang.so', ...]"

  $ LIBCLANG_PATH=<prebuilt>/lib strace -e openat bindgen x.h
  openat(AT_FDCWD, ".../clang-r584948c/lib/libclang.so", O_RDONLY) = 4

so it opens the prebuilt libclang and hard-fails rather than falling
back to the system libclang 18 that is installed on this machine.

Reading bindgen's main branch says why. In bindgen/ir/comp.rs,
CompInfo::from_ty appends each CXCursor_FieldDecl in libclang's visit
order via ci.fields.append_raw_field(field), recording
cur.offset_of_field() beside it; compute_bitfield_units then groups
consecutive bitfields without reordering, and the recorded offset is
consulted only to place bitfields within an allocation unit. Nothing
reconciles the emitted order against the offsets. That bindgen already
has the offsets is the encouraging part: a fix has the information it
needs.
